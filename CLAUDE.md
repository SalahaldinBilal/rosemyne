# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Rosemyne is a ShareX-like screenshot capture/annotate/upload desktop app built with Tauri 2 (Rust backend) and SolidJS + TypeScript (frontend). Windows is the primary target; the Linux capture backend is a stub.

## Commands

- `npm run tauri dev`, run the full app (starts Vite on port 1420 and the Rust backend)
- `npm run dev`, frontend only via Vite (Tauri APIs unavailable)
- `npm run tauri build`, production bundle; `npm run build:debug`, debug bundle
- `cargo check` / `cargo build` inside `src-tauri/`, compile the Rust side alone
- `cargo test` inside `src-tauri/`, run the Rust unit tests

There are no frontend tests or linters configured.

## Architecture

Two Tauri webview windows, both defined at startup:

- **main** (`/` route): screenshot history browser and settings. Created from `tauri.conf.json`; shown/re-created via the tray icon (`focus_or_open_config_window` in `src-tauri/src/lib.rs`).
- **screenshotter** (`/screenshot` route): a borderless transparent window spanning the bounding box of all monitors. Creation/show/hide are platform-specific via the `ScreenshotWindowManager` trait (`src-tauri/src/screenshot_window/`): Windows parks it 32000px off-screen (wraps creation in a per-monitor DPI awareness context, and marks it `WS_EX_TOOLWINDOW` so Chromium/Firefox occlusion trackers keep rendering content behind the live-desktop pick/record overlay instead of pausing and blanking hardware-overlay video), Linux genuinely hides it. If the user destroys it (Alt+F4), `run_callback` in `lib.rs` treats it as a cancelled screenshot and re-creates it.

Screenshot flow: global shortcut or button → `take_screenshot` (`src-tauri/src/screen_manager/commands.rs`) captures the full virtual desktop via GDI (`src-tauri/src/capture/windows.rs`), stores the RGBA image + a WebP preview in `ScreenshotManager`'s in-memory map under a random u16 id, enumerates visible windows (for snap-to-window selection and tagging), then shows the screenshotter window and emits `screenshot://data` to it. The frontend overlay lets the user drag-select a region (or right-click to snap to a window) and add box/text/blur/pixelate overlays, **all overlay rendering is client-side** in `src/helpers/canvasRenderer.ts`: each blur/pixelate canvas composites its region + sampling margin from the capture and the overlays stacked below it (lower effect canvases come from the `effectLayers` registry in `screenshotOverlayState`, invalidated via per-order version counters), so effects stack in z-order with zero IPC during editing. On save, `closeOverlay` hides the window, renders the final image in-page with the same code paths (`renderFinalImage`, on a scene grown by the total effect margin), and sends the raw RGBA through a raw-body invoke (`src/helpers/saveScreenshot.ts`, metadata in the `x-rosemyne-args` header) to `hide_and_save_screenshot`; Rust PNG-encodes, tags visible windows, persists it through the SQLite `HistoryStore`, copies to clipboard, and emits `screenshot://new-saved-image` to the main window. Preview and saved output match by construction.

Overlay attribute defaults (fill/border color, border thickness, text size/font, blur/pixelate intensity) are user-configurable and persisted, under Settings → "Overlay Defaults". `OVERLAY_DEFAULT_ATTRIBUTES` (`src/constants/imageOverlay.ts`) is the built-in baseline; user overrides live in `settings.json` as an `OverlayDefaultOverrides` (Rust: `HashMap<String, HashMap<String, serde_json::Value>>`, values intentionally untyped, Rust doesn't need to understand the attribute schema, only store/return it) via `get_overlay_defaults`/`set_overlay_defaults`. The frontend singleton `src/states/overlayDefaultsState.ts` keeps **one persistent, in-place-mutated store** (`merged`, one entry per overlay type) rather than recomputing/cloning a fresh object on every override change, the Overlay Defaults page binds its controls directly to `merged[type]` slices, and replacing that object wholesale instead of mutating it (e.g. a `createMemo` that re-clones on every change) tears down and rebuilds the DOM under an open color picker, closing it instantly mid-interaction. `defaultAttributesFor(type)` returns an independent snapshot clone for a **newly placed** overlay item (`ImageOverlayContainer.tsx`'s `mouseDownHandler`); placed items are edited afterward via their own per-instance context menu (`ImageOverlayBase.tsx`, `setOverlayItems`), which never touches the shared defaults. Since the screenshotter window is never recreated between captures, `refresh()` re-syncs `merged` from what's actually persisted on every new `screenshot://data` event, so a defaults change made in Settings while the screenshotter was already loaded doesn't leave it stale. The attribute-editing UI itself (`src/components/OverlayAttributeList/`) is shared between the overlay's own right-click menu and the Overlay Defaults page, the color picker's own light/dark text-color heuristic (`@thednp/color-picker`) assumes a translucent color sits over a light checkered backdrop and picks black text whenever alpha ≤ 0.33; Rosemyne renders no such backdrop, so `OverlayAttributeList.module.scss` gives the swatch a flat neutral (`#888`) background instead of the color's own (possibly transparent) one, keeping either text color legible. Box overlays default to a fully transparent fill (`#ff000000`), so a freshly drawn box reads as an outline until the user picks an opaque color.

Video recording flow: the `record` shortcut/button (`record_screen`, or `ShortcutMethod::Record` which toggles stop when a recording is active) shows the same overlay in live record mode (like region-pick: transparent window over the real desktop, no capture), completing the selection invokes `start_recording`, which hides the overlay, tags visible windows, and starts the platform recorder behind the `ScreenRecorder` trait (`src-tauri/src/recording/`): Windows uses the `windows-capture` crate (Windows.Graphics.Capture frames + hardware Media Foundation H.264/AAC MP4 encoder); Linux is a stub. Region recordings are single-monitor (the monitor under the selection's center, clamped, even-aligned): full-monitor captures go through the zero-copy `send_frame` path, regions through per-frame `buffer_crop` + a row flip (the buffer path wants bottom-up BGRA). System audio is WASAPI loopback via `cpal` (input stream on the default *output* device) feeding `send_audio_buffer`, kept alive through silence by a zero-filled output stream; it degrades to a silent recording if unavailable. Encoding runs to a temp `.recording-*.mp4` in the store base; `stop_recording` finalizes it into history via `HistoryStore::save_recording` (rename + `video` row + first-frame WebP thumbnail + the same derived-tag maintenance as `save_rendered`), then copies the saved file itself to the clipboard per the `copy_to_clipboard_on_capture` setting, via `src-tauri/src/file_clipboard/` (CF_HDROP on Windows, `text/uri-list` through `wl-copy`/`xclip` on Linux), the same module behind the `copy_file_to_clipboard` command used by video/file history cards. Only one recording can be active (`RecordingManagerHandler`).

While recording (or scrolling-capturing, below) is active, a small always-on-top status HUD (`capture-hud` window, route `/capture-hud`) shows progress with stop/cancel, and a click-through `capture-border` ring outlines the region; both live in `src-tauri/src/capture_overlay/`, a small module shared by every feature that needs "an outline + a status bar around a region" (currently recording and scrolling capture), since the two are otherwise identical (creation, positioning math, `exclude_from_capture`/`disable_window_dragging`) and only differ in what status they show. Both windows are **pre-created hidden at startup** (`capture_overlay::create_overlay_windows`, called from `run_callback`, which also re-creates them if destroyed) so a feature starting only repositions + shows them via `capture_overlay::show_overlay_windows`/`hide_overlay_windows`; the feature module layered on top is responsible for its own status payload and events (`recording://overlay-shown`/`-hidden` with `RecordingStatus` polling for recording, `scroll-capture://overlay-shown`/`-hidden`/`-progress` for scrolling capture), the frontend's `CaptureHud.tsx` listens for both and renders whichever session is active. On Windows both windows are excluded from capture via `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`.

Scrolling capture flow: the scrolling-capture shortcut/button (`scrolling_capture_screen`) shows the same live-select overlay as region-pick/record (a third `scrollCapture` mode alongside `pickRegion`/`record` on the `Data`/`OverlayMode` shape in `screen_manager/commands.rs`), plus a small `ScrollCaptureLiveParams` panel (scroll distance / frame delay / max frames, see below) seeded from `ScrollingCaptureSettings` every time this mode opens (`screenshotOverlayState.ts`, re-fetched on every `imageData()` change where `scrollCapture` is true, so a Retake re-seeds it too) but never written back to settings, edits there are a one-off override for that capture only, sent as `ScrollCaptureOverrides` alongside the region. Completing the selection invokes `start_scrolling_capture` (`src-tauri/src/scrolling_capture/`), which hides the overlay and runs the whole operation to completion inside that one command (long-running is fine; Tauri commands run as independent async tasks, so this doesn't block anything else). Each loop iteration captures the selected region via the existing GDI path (`CapManager::capture`, unchanged), compares its raw bytes against the previous frame (byte-identical, scrolling produced no visible change, so the bottom's been reached, stop), then scrolls one step via the `ScrollInputManager` trait (`scroll_trait.rs`, platform impls in `windows.rs`/`linux.rs` stub, mirrors `CaptureManager`/`ScreenRecorder`'s per-platform trait shape) before sleeping `frameDelayMs` and repeating, up to `maxFrames` as a safety cap. A wheel notch carries no defined pixel distance (that's entirely up to the receiving app), so the per-step scroll amount is expressed as a `ScrollDistance`, `Percent(u32)` of the captured region's height (the default, 80%) or a flat `Pixels(u32)`, and converted to a notch count once per capture via `notches_for_distance`, using an assumed, approximate pixels-per-notch constant. In practice this hasn't produced a reliably-tunable result in testing (root cause still open), edited via `ScrollDistanceInput`, shared by the Settings page and the live-select overlay's per-instance panel. Before the loop starts, `ScrollInputManager::focus_target` gives the window under the region's center real OS input focus (Windows: `WindowFromPoint` + `SetForegroundWindow`, falling back to a temporary `AttachThreadInput` when the OS foreground lock rejects a direct steal), wheel input, real or synthetic, routes by which window has keyboard focus, not whichever window happens to sit at a point (unlike clicks), so scrolling without this can silently land somewhere other than the target. Every step then goes through the same real, system-level wheel input (`MouseHandler`/`mouse-rs`, `SendInput`/`mouse_event` under the hood, one call per step, no cursor movement) rather than posting a message straight to a hit-tested window handle, since that only ever worked by coincidence. Stop (from the HUD) ends the loop early and keeps whatever frames exist; Cancel discards everything (`Ok(())`, no toast, not treated as a failure).

The captured frames are **not** stitched-and-saved directly. Each captured frame is WebP-encoded (`encode_image_as`, the same helper `ScreenshotManager` uses for its own previews) immediately after capture, the loop only ever holds one raw `RgbaImage` at a time (for the byte-identical-to-last-frame check) alongside the growing `Vec<Vec<u8>>` of already-encoded frames, not a whole session's worth of raw RGBA. `run_capture`'s tail stores that `Vec<Vec<u8>>` (plus the current preview's id/dimensions/frame count/stitch params) in `PendingScrollCaptureHandler` (single-slot, keyed by a random session id the frontend must present back on every review command; `start_scrolling_capture` itself refuses to start a second capture while a review is still pending, since the same slot can't hold two sessions) and runs one auto-parameterized stitch (`window_size_for`, a quarter of the frame height clamped to a sane range; `crop: 5`; `MatchMode::Normal`), or uses the single frame as-is if only one was captured, purely to seed an initial preview, `decode_frames` turns the held WebP bytes back into `RgbaImage`s for the stitcher, which only ever works in raw pixels. That preview is added to `ScreenshotManager` as an ordinary temp image (`Some(Vec::new())` windows, never `None`: `save_rendered_screenshot` treats a `None` list as "the capture no longer exists" and silently drops the eventual save) and a **dedicated `scroll-capture-result` window** (route `/scroll-capture-result`) is built fresh on demand (`scrolling_capture::result_window`), unlike `capture_overlay`/`capture-preview`, this one has no "must appear instantly" requirement, so it's a normal decorated/resizable window, not pre-created hidden and reused; it's genuinely closed (not hidden) when the review ends, and `run_callback`'s `WindowEvent::Destroyed` handler for it (no re-creation, just cleanup) covers the user closing it directly instead of through one of its own buttons. Because it's a brand-new webview every time, its page can't rely on a push event for its initial data, there's no guarantee its JS has loaded and registered a listener before the backend would emit one, unlike the pre-created-hidden windows elsewhere which are already idle and listening long before anything happens to them. So the session (`ScrollCaptureSession`: `sessionId`, `imageId`, `width`, `height`, `frameCount`, `defaultParams`) is stored *before* the window is even created, and the page pulls it via `get_scroll_capture_session` on mount instead, a query is immune to the "was anyone listening yet" race a push isn't. Its image area reuses `ImageViewer` (see below) for pan/zoom, defaulting to fit-to-view on every new image (a stitched capture is often taller than any monitor; opening at 100% would show a small sliver with no hint there's more below).

That page has two steps against the one held session: a **stitch-config** step (window size / seam crop / match mode inputs, window size defaulting to 32 rows (`window_size_for`, only reduced if the captured region itself is shorter than that) and edited via `WindowSizeInput`, a plain number input paired with a floating suggestions dropdown (1, 2, 4, … 1024, doubling each step) built the same way `FilterValueField`'s tag-value autocomplete is, portaled and positioned off the field's own rect, except this list is static so there's no debounce/backend round trip, an explicit Restitch button calling `restitch_scroll_capture`, which re-runs the stitcher against the *same held frames*, no recapturing, swaps in the new temp image, and drops the old one; a frame filmstrip below it lists every captured frame as a thumbnail, clicking one toggles it excluded, kept as a frontend-only `Set<number>` and sent fresh as `excludedFrames` with every restitch call rather than persisted backend-side, restitching always keeps at least one frame, both client-side via `toggleFrame`'s guard and server-side as a real rejection if a stale request somehow gets through empty; thumbnails load from `http://rosemyne-photo.localhost/scroll-frame/<sessionId>/<index>`, serving the already-WebP-encoded held frame directly, no re-encoding) and an **annotate** step (the normal box/text/blur/pixelate/draw tools, reused, see below). Either step can also **Retake** (`cancel_scroll_capture_review` then `scrolling_capture_screen`, dropping the user back at region-picking) or **Discard**. The config step can also skip straight to saving with the full image and no overlays ("Save without annotating"). Either save path renders via the same `renderFinalImage`/`saveScreenshot` (`hide_and_save_screenshot`) pipeline `closeOverlay` already uses, that pipeline was already window-agnostic (an image id + crop box + rendered RGBA bytes, no dependency on which webview called it), so scrolling capture's save reuses it with zero new backend save/persist/clipboard/history code. A successful save (or an explicit Discard) calls `finish_scroll_capture_review`/`cancel_scroll_capture_review`, which frees the held frames, drops whatever temp image was last showing (a harmless no-op if the save already consumed it), and closes the window.

**Annotation UI reuse across two windows**: `ImageOverlayContainer`, `ImageOverlayBase`, `DrawLayer`, `ImageOverlayEffectElem`, and `AnnotationToolBar` (the tool-picker guts extracted from the screenshotter's `ToolBox.tsx`, which now only supplies monitor-anchored positioning) are mounted in *both* the screenshotter editor and the scroll-capture-result window's annotate step, unmodified. Since each Tauri webview is its own independent JS runtime, state was already naturally per-window, the only real blocker was that every one of those components hardcoded a direct import of the screenshotter's singleton (`src/states/screenshotOverlayState.ts`). The fix: `src/states/annotationState.ts`'s `createAnnotationState(previewUrl, toImageCoords?)` factory holds everything generic (selected box, overlay items, tool state, effect layers, draw settings, everything except the screenshotter's own `imageData`/`closeOverlay`/live-select handling), and `src/states/annotationContext.ts` (`AnnotationContext`/`useAnnotationState()`) is what those shared components actually read from; `screenshotOverlayState.ts` calls the factory and re-exports it wrapped with its own screenshotter-specific pieces, and each window's root wraps its content in its own `<AnnotationContext.Provider value={...}>`. `toImageCoords(clientX, clientY)` is how the shared components convert a raw viewport-space point (a mouse event, or a `getBoundingClientRect()` read) into image space; the screenshotter supplies the identity function (its content is never scrolled or zoomed, fixed to the desktop's bounding box with `body { overflow: hidden }` and 1:1 physical-pixel CSS zoom), the scrolling-capture result window supplies one backed by `ImageViewer`'s own pan/zoom transform (below). `ResizableBox` (the generic resize-handle component `ImageOverlayBase` and the result window's own crop tool, `CropSelectionBox.tsx`, both build on) takes this as an optional `toContainerCoords` prop for the same reason: internally it also converts `getBoundingClientRect()`'s two corners (not just the origin) through that function and diffs them to recover the element's container-space size, since the rect itself is always post-transform screen pixels and a naive `width + border` mix of screen and container units silently breaks the moment an ambient scale isn't 1. `toImageDelta(dx, dy)` is `toImageCoords`'s counterpart for a raw screen-pixel *delta* rather than an absolute point (no fixed origin to subtract, just the ambient scale to divide out); needed because `solid-dnd`'s own drag tracking (`ImageOverlayContainer`'s `onDragMove`/`onDragEnd`) reports pointer movement in raw screen pixels regardless of any ancestor transform, so it has to be converted before being added to an item's native-pixel `dimensions`. Both default to identity, matching `toImageCoords`.

`ImageViewer` (`src/components/ImageViewer/`, also the main window's history/file-listing preview) is a self-contained pan/zoom/rotate image viewer (`.Stage`, wheel-zoom toward the cursor, drag-to-pan, its own zoom/rotate toolbar) extended, rather than duplicated, for the scrolling-capture result window's needs. Panning is never gated on the image actually overflowing the viewport, `clampPan` always leaves `PAN_OVERSCROLL` worth of drag room even when the image is fully visible already, so dragging works at every zoom level, not just when zoomed past fit: an optional `overlay` prop renders arbitrary content (the annotation stack, the crop box) inside the *same* `translate/rotate/scale` transform the image itself uses, sized to its natural dimensions, so overlay content built in native image-space pixels stays pixel-aligned at any zoom/pan without its own coordinate math; `hideRotate` hides the rotate controls and keeps rotation at 0, since `overlay` content's coordinate math (and `toImageCoords`, below) only accounts for pan/scale, not rotation; `allowPrimaryPan` (default true) lets the result window disable left-drag panning specifically while an annotation tool wants that gesture (creating a box, drawing), while middle-button drag still pans unconditionally regardless, so free panning is never fully unavailable; `onApi` hands back a `toImageCoords` bound to the viewer's live pan/scale state, once, on mount. The result window puts its `mouseEventHandler.emit("mouseDown", ...)` wiring (the same bus `ImageOverlayContainer`'s tool-creation drag listens on) on its own wrapper *inside* `overlay`, not on `ImageViewer` itself, keeping the pan/draw handoff entirely in the result window's own code, not something `ImageViewer` needs to know about. `ImageViewer`'s own floating toolbar sits at `z-index: 41000`, above every `overlay` z-index in use (annotation items, the crop box, the brush cursor all sit at 30000-40000), so it never ends up hidden under a full-image crop box.

After a capture is saved, or, if auto-upload applies, after that upload concludes so the link is already included, a small preview popup can show near a screen corner. `capture_preview/` (`mod.rs`: `CapturePreviewSettings`, enabled flag, monitor id (`None` = primary, re-resolved by id on every show since monitors can reconnect in a different order), corner, margins, max width/height, auto-dismiss ms (`0` = stays until clicked), left/right click actions (`Nothing`/`Close`/`OpenFile`/`OpenFolder`/`CopyFile`/`CopyLink`), persisted via `get_capture_preview_settings`/`set_capture_preview_settings` and edited in Settings → "Capture Preview"; `commands.rs`: window management) follows the same pre-created-hidden pattern as `capture_overlay`, the `capture-preview` window is pre-created hidden at startup (and re-created if destroyed), transparent/undecorated/always-on-top/skip-taskbar/unfocused, excluded from capture via the same `exclude_from_capture`/`disable_window_dragging` in `capture_overlay` (`pub(crate)`, shared across all three window groups). `notify_history_saved` (`lib.rs`) is the single call site for `capture_preview::commands::trigger`, called after awaiting `maybe_auto_upload`, so the preview always reflects the final state (uploaded or not) instead of needing two call sites. The frontend (`/capture-preview` route) measures its own loaded content (image/video thumbnail natural size scaled to fit the configured max width/height, in physical pixels) and reports back through `show_capture_preview_window(width, height)`, so the window is sized exactly to content with no leftover transparent margin blocking clicks to whatever's behind it. Re-showing the reused window toggles `set_always_on_top(false)` then `(true)`, calling `(true)` alone on an already-topmost window is a no-op and won't re-jump it above the taskbar's own topmost band. Dismissing goes through the custom `hide_capture_preview_window` command rather than the frontend calling the webview's built-in `hide()` directly, that built-in is a window-plugin command gated by ACL (would need an explicit `core:window:allow-hide` grant), while app-defined commands like this one aren't ACL-gated, so routing through it avoids widening the capability surface.

Data lives in `Documents/Rosemyne/`: `images/`, `thumbnails/` (WebP video thumbnails, named `<fileName>.webp`), `history.db` (SQLite), `settings.json`.

Saved screenshot history is a SQLite store (`src-tauri/src/history_store/`), managed as `Arc<HistoryStore>` (a `Mutex<Connection>`), separate from `ScreenshotManager` (which now only holds in-memory temp captures). The main window loads it **paginated, sorted and filtered server-side** with keyset pagination: `query_history` takes a sort spec (`date`|`name` × `asc`|`desc`) and an optional `{key, id}` cursor where `key` is the sort column's value on the last row (the row count is computed only on the cursor-less first page; name ordering is `COLLATE NOCASE`), and the frontend renders a row-virtualized infinite list (`src/pages/Main/Main.tsx`) that threads `nextCursor` through `loadMore`. The filter tree is **compiled to SQL** (`history_store/compile.rs`): each condition becomes an `IN (SELECT history_id FROM tag_index …)` subquery against the `tag_index` table (one row per scalar tag value, keyed by JSON-stringified path + kind `s`/`n`/`b`), so positive operations (equals, ranges, contains/starts/ends via `instr`/`substr`) never parse tag JSON at query time; conditions on the virtual `$file` paths compile to plain column predicates instead (see Conventions). Only inexact compilations, tag `notEquals` (satisfiable by a missing key), non-empty `fuzzy` (subsequence match) and same-element scoped groups (below), append a `filter_match(tags, file_name, file_path, type)` residual: a registered SQLite scalar function (`history_store/filter.rs`) evaluating the `FilterNode` tree per row over the `$file`-augmented tags, a faithful Rust port of `src/states/tagFilterState.ts` (`resolvePath` + `applyOperation`; `fuzzy` is approximated) and the semantic source of truth the compiler's prefilter must stay a superset of. The filter UI's path/type schema is a **cache** in the `meta` (`tag_schema` blob) table read by `get_tag_metadata`; value autocomplete is **queried on demand** via `suggest_tag_values` (case-insensitive substring over `tag_value_counts`, most-common first, LIMIT 50) rather than shipped with the metadata, see Conventions.

A filter group can carry a **scope** (`FilterGroup.scope`, a tag path): its children are then matched against *one element of that array at a time*, with their own paths relative to it, so "the same window is both `firefox` and covers >50%" is expressible where two sibling conditions on `Windows › …` are independently satisfiable by two different windows. Scopes nest (a scoped group inside a scoped group resolves relative to its parent's current element), and only object-array paths are offered as scopes since scoping to a single object is what an unscoped group already does. Both evaluators resolve them through `resolve_scope`/`resolveScope`, the containers at a path rather than the scalars under it, and a scope with no candidates (missing key, empty array) fails the group, while a scoped group with no children still matches everything like any empty group. `compile.rs` threads an absolute path prefix and flattens scopes back out (`prefix ++ path`), which is exactly the unscoped semantics and therefore a superset: a scoped `AND` over two or more children is compiled **inexact** so `filter_match` enforces the same-element part, while a scoped `OR` (or a single child) is equal to the flattened form and stays exact. In the UI (`FilterGroupView`) the scope is a per-group Select on nested groups only, the root stays unscoped so `$file` conditions keep resolving; picking one resets descendant paths (they were relative to the old scope) and re-roots the child path pickers at the scope's sub-schema, with the absolute prefix threaded down to `FilterValueField` since `suggest_tag_values` is keyed by absolute path.

Saved capture file names come from the `fileNameTemplate` setting, expanded and sanitized in `history_store/store.rs` (`expand_file_name_template`): `${process}`/`${windowTitle}` (the window covering the largest share of the capture, from the tags), date/time parts, `${width}`/`${height}`, `${random}`/`${random:N}` (N clamped 1–32) and `${guid}`; default `${process}_${random:10}`, `.png` (screenshots) or `.mp4` (recordings) appended, `-1`/`-2`… on collision. Imported files keep their original names, this is a separate setting from where they're placed (below).

Destination **directories** (distinct from file names, above) come from the `uploadPath` ("save path template") setting, expanded by `expand_save_dir` (`history_store/store.rs`, `pub(crate)`): always rooted at `<base>/files/`, with the expanded template as a subpath (`${year}`/`${month}`/`${day}`/`${hour}`/`${minute}`/`${second}`/`${type}`; root/parent path components are stripped so it can't escape `files/`), default `${year}-${month}`. Every history-creating path uses this, fresh captures/imports (`import_file`) and ShareX migration (`sharex_migration/migration.rs`) alike, so imported files land organized the same way a fresh capture would, instead of one flat dump folder. ShareX migration computes the directory **per row from that row's own original ShareX date**, not the migration's run time, so old screenshots stay organized under their original period instead of all bucketing into the current month.

Images are served to the frontend through the custom `rosemyne-photo` URI scheme registered in `lib.rs`: `http://rosemyne-photo.localhost/saved/<fileName>` (from disk; honors `Range` requests with 206 chunks so `<video>` streams and seeks without loading whole files), `/thumb/<fileName>` (WebP video thumbnail from `thumbnails/`, 404 when absent) and `/preview/<id>` (in-memory WebP preview, also the bitmap source for all canvas rendering). `/saved` and `/preview` send `Access-Control-Allow-Origin`, so canvases stay untainted (`getImageData`, and the video-thumbnail generation in `src/helpers/videoThumbnail.ts`).

Video thumbnails are always generated **client-side**, never by Rust: `generateVideoThumbnail`/`captureVideoFrame` (`src/helpers/videoThumbnail.ts`) load the video into a hidden `crossorigin` `<video>` element, seek to an early frame, draw it to a canvas, and `canvas.toBlob(..., "image/webp")`, the browser's own WebP encoder, no server-side encoding involved, then ship the bytes via the raw-body `save_video_thumbnail` command (`HistoryStore::save_thumbnail_bytes` just writes them to `thumbnails/` as-is). Two call sites: `Main.tsx`'s video cards generate lazily when their thumbnail `<img>` 404s (i.e. only for videos the user actually scrolls past), and `ShareXImport.tsx` also generates proactively right after a real import for every video at least `LARGE_VIDEO_BYTES` large still missing one (`list_videos_missing_thumbnail`/`HistoryStore::videos_missing_thumbnail`), so a big migration doesn't leave large videos stuck on a placeholder indefinitely.

Screenshot/video cards (`Main.tsx`) support dragging the card **out to another app** as a real OS file drag via `tauri-plugin-drag`'s `startDrag` (not HTML5 drag-and-drop): the dragged item is the card's actual saved file, with a small (≤128px) preview icon rendered server-side by `HistoryStore::drag_icon_path`/`get_drag_icon` (from the image itself, or the video's thumbnail if it has one; falls back to no custom icon, just the OS default cursor, for videos without a thumbnail yet or plain files, since Windows' image decoder can't preview those anyway). Dropping a card back onto the app's own window is a no-op, not a duplicate: `HistoryStore::import_file` checks whether the source path already lives under the store's own base directory and returns `None` without copying/recording if so.

Frontend↔backend calls go through `safeInvoke` (`src/helpers/safeInvoke.ts`), which types every Tauri command name, its args, and return type in the `Commands` map. When adding or changing a `#[tauri::command]`, register it in the `invoke_handler` list in `lib.rs` **and** update the `Commands` type. Rust structs are serialized `camelCase` (serde rename) to match the TS types in `src/types/`. One exception: `hide_and_save_screenshot` takes a raw binary body (`tauri::ipc::Request`) and is invoked via `src/helpers/saveScreenshot.ts` instead of `safeInvoke`.

Global state on the frontend uses the `createRoot(useXStateInner)` singleton pattern (`src/states/`). The `@core` Vite alias maps to `src/`.

## Conventions

- **Let code explain itself.** Default to no comments. Add one only for a genuinely non-obvious invariant, gotcha, or reason, never to restate what the code already says. Keep it to one short line, not a paragraph.
- Emitting events from Rust to the frontend must go through the `emit_on_main_thread!` macro (defined in `lib.rs`), emitting cross-thread can deadlock with WebView2 on Windows (tauri-apps/tauri#9453, #11787). Never call `.emit()` directly.
- Tagged Rust enums exposed to the frontend use `#[serde(tag = "type", content = "data", rename_all = "camelCase")]`; mirror them in TS with the `BaseUploaderType`-style discriminated unions in `src/types/request.ts`. **The enum-level `rename_all` only cases the variant tag, not fields inside a struct variant**, a multi-word field name on a struct variant (e.g. `response_headers`) is serialized as-is unless that variant also gets its own `#[serde(rename_all = "camelCase")]` (see `UploaderBodyHandler::FormData`, `OverlayInstruction::Box`). Forgetting this silently desyncs the JSON from the TS type instead of failing to compile, always add the per-variant attribute on any struct variant with a multi-word field.
- **Every mutation of the `history` table must keep the derived tag tables in sync.** There are two: the tag-metadata cache (`tag_schema` blob in `meta` + `tag_value_counts`, read by `get_tag_metadata` instead of scanning `history`) and the `tag_index` query-acceleration table (read by the compiled filter in `compile.rs`). Any insert/delete that touches a row's `tags` must, in the same operation, merge the schema, increment/decrement the value counts (prune rows hitting 0), and insert/delete the row's `tag_index` entries. Route all history writes through `HistoryStore` methods (`save_rendered`, `insert_batch`, `delete_with_file`), they already do this; don't write the `history` table directly. Both are derived indexes: they are fully rebuilt by a one-time scan on open whenever `meta.metadata_status` isn't the current `METADATA_STATUS_BUILT` value (the status is set to `building` before the scan so an interrupted rebuild is detected and restarted). If you add a new history-mutating path, change the tag shape, or change what the derived tables store, update the maintenance alongside it and bump `METADATA_STATUS_BUILT` to force a rebuild.
- `tag_index` and `filter_match` (`filter.rs`) implement the same filter semantics twice: the compiled SQL must match a **superset** of what `filter_match` matches (exactly equal when `CompiledFilter::exact`). `collect_index_entries` in `compile.rs` must flatten tags exactly like `resolve_path` in `filter.rs` resolves them (arrays transparent, objects extend the path, nulls dropped, booleans kept); group scopes are the one case where the prefilter is deliberately a strict superset. When touching filter semantics, update both and extend the `compiled_queries_match_reference_eval` parity test in `store.rs`.
- **Every derived reactive value in a SolidJS component must be wrapped in `createMemo`**, never a plain `const x = () => …` arrow function, this holds regardless of how cheap the computation is, not just for expensive/multi-read cases. This applies whether the reactive dependency is closed over (a signal/prop/store field read directly in the body) or passed in as an argument that is itself reactive, a function called with a reactive value (e.g. `screenshot.fileName` from a store row) needs its call site memoized just as much as one with no arguments at all. The only real exemptions: plain functions with no reactive reads inside them at all (pure, generic, stateless), and imperative helpers only ever invoked from event handlers/async flows and never read reactively in the render tree (e.g. `currentFilter()` in `Main.tsx`).
- A settings row `<label>` wrapping a checkbox forwards clicks landing on any non-form-control descendant (e.g. a custom `Select`/`Input`) to the checkbox, silently toggling it. Only pure toggle rows (checkbox + static text) are `<label>`s; a row with any interactive sub-control uses a plain `<div>` instead (see `GeneralSettings.module.scss`'s `.SettingRow` comment).
- **Top-level tag keys starting with `$` are a reserved system namespace.** The only current member is the virtual `$file` tag (`["$file","Name"|"Path"|"Type"|"DateTime"|"Size"]`), which exposes the `file_name`/`file_path`/`type`/`date_time_ms`/`file_size` columns through the normal filter machinery: `get_tag_metadata` injects its schema at read time (`Size`'s schema `type` is `"byteSize"`, a frontend-only kind rendering `FileSizeField`, a unit-picker like `DurationField`'s), `compile.rs` (`file_column`) turns its conditions into column predicates, `filter.rs` (`augment_tags`) inserts a `$file` object into each row's parsed tags before residual evaluation, and `suggest_tag_values` special-cases its autocomplete (numeric fields, `DateTime`/`Size`, return no suggestions). Every operation except `fuzzy` compiles exactly for the always-present text columns and `DateTime`; `Size` (backed by nullable `file_size`) is treated the same as always-present for simplicity, so `notEquals` on a row with no recorded size (a rare failed-`stat` case in `save_recording`) is a known, accepted narrow divergence from the reference evaluator rather than specially handled. `filter.rs` (`augment_tags`) omits `Size` entirely (not `null`) when `file_size` is absent, so it resolves as a missing key like any other optional tag. The filter UI renders `$`-keys prettified (`$file` → "File", `keyLabel` in `FilterConditionView`). `$file` entries are never written to `history.tags` or `tag_index`, they're synthesized at query time. If user-defined custom tags are ever added, reject keys starting with `$` at that boundary so collisions stay impossible.
